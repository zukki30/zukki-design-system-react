# 要件: main へのマージで自動的にリリースタグを打つ

## 背景

このライブラリは npm へ publish せず、**git 経由で install して使う**（`README.md:5-13`）。

```bash
pnpm add github:zukki30/zukki-design-system-react
```

この形式には利点もあるが、**バージョンを固定する手段がタグしかない**。そして現状このリポジトリには **git タグが 1 つも無い**（`git tag` の結果が 0 件）。

結果として、利用側は次の状態に置かれている。

- `pnpm add github:zukki30/zukki-design-system-react` は **常に main の最新コミット**を指す
- install し直すたびに中身が変わりうる。`pnpm-lock.yaml` にはコミット SHA が記録されるため一度入れれば固定はされるが、**「どのバージョンを使っているか」が人間に読める形で残らない**
- 破壊的変更が入っても、利用側は気づく手段がない
- README にバージョンを固定する方法を案内できない

`package.json` の `version` は `3.0.0` になっており、バージョン番号自体は管理されている。**これをタグとして外に出す経路が無いだけ**である。

## 現状

すべて実測で確認した事実である。

### リポジトリの設定

| 項目 | 現状 | 影響 |
| --- | --- | --- |
| 公開範囲 | **public** | git install に認証が要らない。タグを打てば誰でも固定できる |
| `main` の branch protection | **無し**（API が 404 を返す） | main への直接 push が可能。**マージ時点で CI が通っている保証が無い** |
| マージ方式 | squash / merge commit / rebase すべて許可 | コミットメッセージの形が一定しない |
| `delete_branch_on_merge` | `true` | — |
| git タグ | **0 件** | 固定手段が無い |

### 既存のワークフロー

| ファイル | トリガー | 内容 |
| --- | --- | --- |
| `ci.yml` | `pull_request` / `push: [main]` | lint / format / typecheck / test / check:css-types / a11y / dist |
| `assign-pr-author.yml` | `pull_request` | PR 作成者を assignee にする |
| `claude-review.yml` / `codex-review.yml` | — | AI によるレビュー |

`ci.yml` の `dist` ジョブは `pnpm install`（= `prepare` でフルビルド）と `pnpm verify:dist` を実行しており、**配布物として成立しているかの検査が既にある**。リリース時にこれを再利用できる。

`assign-pr-author.yml` は `gh` CLI + `GH_TOKEN` + 最小の `permissions` という書き方をしている。本 spec もこの流儀に揃える。

### 配布物の作られ方

`dist/` はリポジトリに含めず、`prepare` スクリプトが install 時にビルドする（`AGENTS.md`「配布物」）。つまり**タグが指すのはソースであり、ビルド済み成果物ではない**。タグを打つ前に「そのコミットが実際にビルドできる」ことを確かめる意味は、publish する場合より大きい。

## 方針（決定済み）

事前のやり取りで次を決定した。要件はこれを前提とする。

| 論点 | 決定 |
| --- | --- |
| バージョン番号の決め方 | **`package.json` の `version` を単一の正とする。** PR の中で人が上げ、main へのマージ時にその値でタグを打つ |
| 同時に作るもの | **タグ + GitHub Release（リリースノート自動生成）** |
| GitHub Packages への publish | **行わない。** 本 spec のスコープ外 |

`package.json` を正とする理由は次の 3 点。

1. 破壊的変更かどうかの判断を人が持てる。デザインシステムでは「見た目が変わる」「prop 名が変わる」といった変更の重大さを機械が判定しきれない
2. squash merge の件名の書き方に結果が左右されない（このリポジトリは 3 つのマージ方式をすべて許可している）
3. 追加の依存パッケージが要らない

## 機能要件

### FR-1: main へのマージで自動的にタグが作られる

- `main` への push をトリガーに、`package.json` の `version` を読み取る
- `v<version>` 形式のタグを作成する（例: `version: "3.1.0"` → `v3.1.0`）
- 人手の操作を必要としない

`v` を前置するのは、npm / pnpm の git 依存が `#semver:^3.0.0` 形式の範囲指定を解決するときに `v` 付きタグを semver として解釈するため。利用側が範囲指定を使えるようになる。

### FR-2: 冪等であること

`main` への push は、リリースを伴わない変更（ドキュメント修正など）でも発生する。

- **`v<version>` タグが既に存在する場合は、何もせず正常終了する**。エラーにしない
- 同じバージョンで複数回 main へ push しても、タグや Release が重複・上書きされない

これは「`version` を上げ忘れたときに黙ってタグが付かない」という安全な失敗の仕方でもある。誤ったタグが打たれるよりはるかに安全な側に倒れる。

### FR-3: 何が起きたかが分かること

FR-2 の「何もしない」は、そのままでは**上げ忘れと区別がつかない**。

- タグを作らなかった場合、**その理由（`version` が変わっていない）をワークフローの実行結果から読み取れること**
- タグを作った場合も、どのバージョンを作ったかが分かること

### FR-4: GitHub Release を作り、リリースノートを自動生成する

- タグ作成と同時に GitHub Release を作成する
- リリースノートは GitHub の自動生成機能で埋める（前回のリリースからマージされた PR の一覧）
- Release のタイトルはタグ名と揃える

### FR-5: タグを打つ前に、そのコミットが配布物として成立することを検証する

`main` に branch protection が無いため、**マージ時点で CI が通っている保証が無い**。壊れたコミットにタグが付くと、利用側が `#v3.1.0` で固定した先が install できない状態になる。

- タグを作る前に、対象コミットが**ビルドでき、配布物の検査を通る**ことを確認すること
- 検証に失敗した場合はタグも Release も作らないこと

検証の範囲（ビルドだけか、lint / test まで含めるか）は設計フェーズで決める（論点 1）。

### FR-6: ドキュメントを更新する

- `README.md` のインストール手順に、**タグでバージョンを固定する方法**を追記する
- `AGENTS.md` に**リリース手順**（`version` を上げて PR を出す、という運用）を追記する。規約の唯一の正は `AGENTS.md` であるため、`CLAUDE.md` には書かない

## 非機能要件

### NFR-1: 権限を最小にする

- ワークフローの `permissions` を明示的に宣言し、必要なスコープだけを与える
- 個人の PAT を Secrets に置かない。`GITHUB_TOKEN` で完結させる

`GITHUB_TOKEN` は実行ごとに自動発行され、実行終了とともに失効する。期限管理も漏洩時の影響範囲も PAT より小さく、**これで足りるなら PAT を使わないのが現在の推奨**である。

### NFR-2: `GITHUB_TOKEN` が他のワークフローを発火しない制約を踏まえた設計にする

**`GITHUB_TOKEN` で作成したタグや push は、他のワークフローをトリガーしない。** これは GitHub がワークフローの無限ループを防ぐために設けている仕様である。

したがって「タグ作成をトリガーに別のワークフローを動かす」構成は `GITHUB_TOKEN` では成立しない。本 spec の範囲では**必要な処理を 1 つのワークフロー内で完結させる**ことで回避する。この制約と回避方法をワークフローのコメントに残し、将来 publish 等を足すときに踏み抜かないようにすること。

### NFR-3: 実行の重なりを避ける

`main` へ短時間に複数回 push された場合に、同じバージョンのタグを同時に作ろうとして競合しないこと。ただし**リリース処理を途中でキャンセルしない**こと（`ci.yml` の `cancel-in-progress: true` とは要件が異なる）。

### NFR-4: 既存のワークフローと実装の流儀を揃える

- Node のバージョン指定など、`ci.yml` と重複する箇所は同じ値・同じ書き方にする
- 判断を伴う箇所には理由をコメントで残す（既存ワークフローと同じ）

### NFR-5: 既存の開発フローを壊さない

- `ci.yml` の実行内容・実行時間に影響を与えないこと
- 通常の PR 作業に新たな手順を増やさないこと（`version` を上げるのはリリースしたい PR だけでよい）

## スコープ外

- **GitHub Packages / npm への publish** — 今回は行わない。git install のまま運用する
- **`CHANGELOG.md` の生成** — GitHub Release のノートで代替する。ファイルとして持つと二重管理になる
- **`version` の自動採番** — 人が上げる方針を採ったため
- **`main` の branch protection 設定** — GitHub 上のリポジトリ設定であり、ワークフローの実装とは別作業。ただし FR-5 の判断に影響するため、設計フェーズで言及する
- **過去のコミットへ遡ってタグを打つこと** — `v3.0.0` を現在の main に打つかは運用判断として別途決める

## 判断が必要な論点

設計フェーズで決める。

### 論点 1: タグを打つ前の検証をどこまでやるか

`main` に branch protection が無いことが前提。

| 案 | 内容 | 評価の観点 |
| --- | --- | --- |
| A. ビルドと `verify:dist` のみ | `pnpm install`（= `prepare` でビルド）+ `pnpm verify:dist` | 「install して使えるか」に直結する最小限。実行時間が短い |
| B. CI 相当をすべて再実行 | lint / format / typecheck / test / a11y / dist | 確実だが、`ci.yml` と完全に重複し、リリースのたびに数分を再消費する |
| C. `ci.yml` の完了を待つ | `workflow_run` で CI の成功を待って起動 | 重複が無い。ただし `workflow_run` は「default branch の定義が使われる」など癖があり、読み解きづらい |
| D. branch protection に委ねる | main への直接 push を禁じ、PR で CI 必須にする。リリース側は検証しない | 根本的で、リリース以外にも効く。ただしリポジトリ設定の変更が必要 |

A と D は併用できる。

### 論点 2: タグと Release をどう作るか

| 案 | 内容 |
| --- | --- |
| `gh release create --generate-notes` | タグ作成・Release 作成・ノート生成が 1 コマンドで済む。タグが存在しなければ GitHub 側が軽量タグを作る。`gh` は runner にプリインストール済み |
| git でタグを push し、別途 Release API を叩く | 注釈付きタグにできる。手順は増える |

### 論点 3: リリースノートのカテゴリ分けをするか

`.github/release.yml` を置くと、PR のラベルごとに「Features」「Bug Fixes」などへ分類できる。今回入れるか、まず素の自動生成で運用してみるか。

### 論点 4: `version` の上げ忘れをどこまで支援するか

FR-3 で「タグを作らなかった理由が分かる」ところまでは要件に入れた。それ以上（PR で version 差分が無いと警告する等）を今回やるかどうか。

## 受け入れ条件

- [ ] `package.json` の `version` を上げた PR を main にマージすると、`v<version>` タグが自動で作られる
- [ ] 同時に GitHub Release が作られ、リリースノートに前回リリース以降の PR が並ぶ
- [ ] `version` を変えない PR をマージしても、タグも Release も作られず、ワークフローは成功する
- [ ] タグを作らなかった場合、その理由が実行結果から読み取れる
- [ ] ビルドまたは配布物の検査に失敗したコミットには、タグも Release も作られない
- [ ] ワークフローの `permissions` が明示され、必要最小限になっている
- [ ] PAT を Secrets に追加していない
- [ ] `README.md` にタグでバージョンを固定する方法が書かれている
- [ ] `AGENTS.md` にリリース手順が書かれている
- [ ] 既存の `ci.yml` の挙動が変わっていない
- [ ] **実際に main へマージしてタグと Release が作られることを確認した**
