# 要件: a11y エラーを検出できる環境の構築

対象 Issue: [#83 a11y でエラーがでているか確認できる環境を作成する](https://github.com/zukki30/zukki-design-system-react/issues/83)

## 背景

現状、このリポジトリには **a11y を検査する仕組みが実質的に存在しない**。

| 層 | 現状 |
| --- | --- |
| ESLint | `eslint-plugin-jsx-a11y` は devDependencies に入っており `eslint.config.js` の `plugins` にも登録済み。ただし**ルールが 1 つも有効化されていない**ため何も検出しない |
| Vitest | `axe-core` 系のパッケージなし。33 個の spec は Testing Library ベースで、a11y の検証は `getByRole` 程度の間接的なもののみ |
| Storybook | `@storybook/addon-a11y` 未導入 |
| CI | `lint:check` / `format:check` / `typecheck` / `test` の 4 ジョブのみ。a11y 専用の検査なし |

### AI エージェントによる開発を前提とする

このリポジトリのコンポーネント実装は AI エージェントが行う。そのため **「人間が Storybook の画面を目視して気づく」ことを前提にした仕組みは要件を満たさない**。

`@storybook/addon-a11y` は単体では Storybook UI 上のパネル表示にとどまり、エージェントからは不可視である。同アドオンが機械判定可能な検査になるのは、`parameters.a11y.test: 'error'` を設定し、かつ同梱の `afterEach` フックを実行するテストランナー（`@storybook/addon-vitest`）と組み合わせたときに限られる。

したがって本件の成果物は、**すべて終了コードで合否が判定でき、CI でブロックされること**を必須条件とする。

### jsdom では検査できない領域

`axe-core` を jsdom 上で動かす構成では、以下が原理的に検査できない。

- `color-contrast`（実レンダリングと計算済みスタイルが必要）
- フォーカスリングの視認性
- ターゲットサイズ（クリック領域の大きさ）
- 要素の重なり・はみ出しによる不可視化

本デザインシステムは色をすべて `src/styles/theme.css.ts` の `vars` 経由の CSS 変数で当てているため、**色に起因する事故が最も起きやすい**にもかかわらず、jsdom ではその領域が丸ごと検査対象外になる。人間開発であれば Storybook の目視が保険になるが、エージェント開発ではその保険が存在しない。

よって実行時の検査は **実ブラウザ上で行う**ことを必須とする。

## 機能要件

### FR-1: 静的解析で a11y 違反を検出する

- `eslint-plugin-jsx-a11y` の推奨ルールセットを有効化する
- 既存の `pnpm lint:check` コマンドでそのまま検出できること（新規コマンドを増やさない）
- 違反があれば非ゼロの終了コードで終了すること

### FR-2: 実行時に実ブラウザで a11y 違反を検出する

- 全ストーリー（19 ファイル・約 102 ストーリー）に対して `axe-core` による検査を実行する
- 検査は実ブラウザ上で行い、`color-contrast` を含むレンダリング依存のルールが有効であること
- 違反があればテストが失敗すること

#### 補足: 操作後の状態の検査について（2026-08-26 訂正）

当初この項に「既に `play` を持つ 15 ファイルについては `play` 実行後の状態に対して検査されること」と記載していたが、**これは誤りである**。`grep "play:"` が `display:` に誤マッチしていたもので、実際には **`play` 関数は 1 つも存在しない**。

このため、ストーリーが既定で描画している状態のみが検査対象となる。とくに `Dialog` は `useState(false)` で閉じた状態から始まるため（`Dialog.stories.tsx` の `DialogDemo`）、**このままではダイアログ本体が一度も検査されない**。フォーカストラップやラベル付けなど a11y 上の要点を最も多く含むコンポーネントが未検査になる。

この扱いは「決定事項 D-7」で定める。

### FR-3: CI で検査が実行されブロックされる

- FR-1 / FR-2 の検査が Pull Request 時に CI で実行されること
- 違反があれば CI が失敗し、マージがブロックされること
- 既存 CI の方針（`fail-fast: false` で 1 つ落ちても他の結果が見えること）を踏襲すること

### FR-4: ローカルでも同じ検査を実行できる

- CI と同じ検査を単一のコマンドで実行できること
- AI エージェントが実装後の自己検証として実行できる粒度であること

### FR-5: 違反内容が機械可読な形で出力される

出力には最低限、以下が含まれること。

- 違反したルール ID（例: `color-contrast`）
- 該当するストーリー名 / 該当要素
- 対処方法を示す参照 URL

### FR-6: 開発中の目視確認手段も残す

- Storybook 上で a11y 違反を確認できるパネルを利用可能にする
- これは FR-1〜FR-5 の代替ではなく、人間が開発・レビューする際の補助として位置づける

## 非機能要件

### NFR-1: 既存テストを壊さない

- 現行の jsdom ベースの 33 spec は従来どおり動作すること
- ブラウザ実行の検査とは実行環境を分離すること
- `pnpm test` の既存の役割を変えないこと

### NFR-2: CI 実行時間の増加を抑える

- ブラウザは Chromium のみとし、不要なブラウザをインストールしないこと
- CI 上でブラウザバイナリをキャッシュすること

### NFR-3: 依存バージョンの整合性

- Storybook 関連は現行の `10.5.10` と一致させること
- Vitest 4 系と互換なパッケージのみを採用すること
- Node 24.14.1 / pnpm 10.33.0（`.mise.toml`）で動作すること

### NFR-4: ドキュメント

- 導入した検査の実行方法と、違反が出たときの対処方針を `CLAUDE.md` に追記すること
- ストーリー起因のノイズを抑制する設定を入れる場合、その理由をコメントとして残すこと

## 既知の対応事項

### 静的解析で既に検出される違反（実測値）

一時 config で `jsx-a11y` の推奨ルールを当てて計測した結果、**3 件**検出された。

| ファイル | ルール | 対応方針 |
| --- | --- | --- |
| `src/components/Card/Card.stories.tsx:14` | `anchor-is-valid` | ストーリー内の `href="#"`。実害のあるリンクを持たせるか、ストーリー用途として除外するかを設計フェーズで決める |
| `src/components/Dialog/Dialog.tsx:191` | `click-events-have-key-events` | `<dialog>` のオーバーレイクリック用 `onClick`。ESC は `onCancel` がネイティブに処理しているため**誤検知**。理由コメント付きの局所 disable とする |
| `src/components/Dialog/Dialog.tsx:191` | `no-noninteractive-element-interactions` | 同上 |

### ストーリー起因のノイズ

既存ストーリーは 1 つのストーリー内に複数バリアントを並べ、`<h4>` などの素の見出しで区切る構成になっている（例: `Button.stories.tsx`）。この構成のまま実ブラウザで axe を実行すると、**コンポーネントの欠陥ではなくストーリーの組み方に起因する違反**が出る可能性が高い。

- `heading-order`（`h1`〜`h3` を挟まずに `h4` が現れる）
- `region` / `page-has-heading-one` などの文書構造レベルのルール

これらをどう扱うか（ルール単位で無効化するか、ストーリー側を組み替えるか）は設計フェーズで決定する。**コンポーネント自身の欠陥を見逃す方向の抑制はしない**ことを条件とする。

### 既存コンポーネントの違反への対処方針

実ブラウザでの検査を有効化した時点で、既存コンポーネントに違反が検出される可能性がある（特に `color-contrast`）。

本 spec のスコープは **「検出できる環境を作ること」** であり、検出された個別の違反をすべて修正することは含めない。ただし違反を放置したまま CI を通すことは FR-3 に反するため、以下の方針とする。

1. まず検査を実行し、違反の件数と内容を洗い出す
2. 軽微かつ明確なものは本対応で修正する
3. 判断が必要なもの・デザイン変更を伴うものは `parameters.a11y.test: 'todo'` で一時的に非ブロック化し、**別 Issue を起票して追跡する**
4. `todo` として残した項目は要件ファイルまたは Issue に一覧として明記する

### D-7: 操作しないと到達できない状態の扱い

上記の訂正を受けて、各コンポーネントの「既定のストーリーで描画されない状態」を調査した結果は以下のとおり。

| コンポーネント | 状況 | 対応 |
| --- | --- | --- |
| `Tooltip` | `open?: boolean` prop を持ち、ストーリーが既に `open: true` で表示状態を描画している | **対応不要**（既に検査される） |
| `Select` | ネイティブの `<select>`。展開後のリストは UA が描画するため axe の検査対象外 | **対応不要** |
| `Dialog` | `DialogDemo` が `useState(false)` で閉じた状態から始まるため、ダイアログ本体が描画されない | **要対応** |

`Dialog` は `open` prop で内部的に `showModal()` を呼ぶ設計のため、**`open` を真で始めるストーリーを 1 つ追加すれば `play` 関数なしで検査対象にできる**。

本 spec の目的は「a11y エラーを検出できる環境を作ること」であり、ライブラリ中で最も a11y 上の要点が多い `Dialog` が一度も検査されない状態では FR-2 を満たしたとは言えない。したがって **この 1 ストーリーの追加は本対応に含める**。

一方、これを超える範囲（全コンポーネントへの `play` 関数の追加によるフォーカス状態・入力後状態の網羅）はスコープ外とし、必要が生じた時点で別 Issue とする。

## スコープ外

- **jsdom + `axe-core` を各 spec に個別に書く構成**（当初案 2）。実ブラウザ検査とルール範囲が大きく重複し、設定を二重に保守することになるため採用しない。ストーリーで再現できない状態が見つかった場合は、ストーリー側に `play` を追加して実ブラウザ検査に寄せる
- 既存コンポーネントの a11y 不備の全面的な修正（上記「既存コンポーネントの違反への対処方針」に従い、別 Issue で追跡する）
- E2E テスト基盤の構築全般（a11y 検査に必要な範囲を超えるものは扱わない）
- Chromatic 等のビジュアルリグレッションテスト

## 受け入れ条件

- [ ] `pnpm lint:check` が `jsx-a11y` の違反を検出し、非ゼロ終了する状態を作れる
- [ ] 全ストーリーに対する実ブラウザでの axe 検査が単一コマンドで実行でき、違反があれば非ゼロ終了する
- [ ] `color-contrast` ルールが実際に評価されていることを確認できる
- [ ] 既存の `pnpm test`（jsdom / 33 spec）が従来どおり成功する
- [ ] CI の Pull Request 実行で上記 2 種類の検査が走り、違反時にジョブが失敗する
- [ ] 上記「静的解析で既に検出される違反」3 件が解消または妥当な理由付きで抑制されている
- [ ] `todo` として残した違反があれば、その一覧と追跡先が記録されている
- [ ] `CLAUDE.md` に検査の実行方法と違反時の対処方針が追記されている
